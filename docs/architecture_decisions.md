# Architecture Decision Record — Invoice Generator SaaS Backend

## ADR-001: UUID Primary Keys
**Date:** 2026-08-08
**Status:** Adopted

All tables use `uuid` PKs generated via `gen_random_uuid()`.

**Rationale:** UUIDs prevent sequential-ID enumeration attacks, are safe to generate on either server or client side (though we always generate server-side), and work well with distributed or multi-tenant systems.

## ADR-002: business_id Denormalization on invoice_items and payments
**Date:** 2026-08-08
**Status:** Adopted

`invoice_items` and `payments` carry a `business_id` column even though it is derivable via a JOIN through `invoices`.

**Rationale:** RLS policies run on every row access. A JOIN-based RLS check on these tables would force a `public.invoices` scan on every row evaluated. Denormalizing `business_id` lets the RLS helper functions check the row directly with a cheap index lookup. The `before_invoice_item_change` trigger validates that `invoice_items.business_id` matches the parent invoice's `business_id`, preventing inconsistency.

## ADR-003: SECURITY DEFINER Functions for RLS Helpers and Bootstrap Triggers
**Date:** 2026-08-08
**Status:** Adopted

Three functions use `SECURITY DEFINER`:
1. `handle_new_user()` — writes to `profiles` during `auth.users` INSERT.
2. `handle_new_business()` — writes the owner row to `business_members` during `businesses` INSERT.
3. `is_business_member()`, `is_business_admin()`, `is_business_owner()`, `get_business_role()`, `generate_invoice_number()` — read/write data that RLS would normally block.

**Rationale:**
- Bootstrap functions (1 & 2): At the moment of first INSERT, the user has no existing rows in `profiles` or `business_members`. Standard RLS would block the INSERT because the membership check would return false. SECURITY DEFINER resolves this chicken-and-egg problem.
- RLS helpers (3): These functions query `business_members`. If they ran under the caller's RLS context, the RLS policies on `business_members` (which call these same functions) would recurse infinitely.

**Mitigations:** All SECURITY DEFINER functions have `SET search_path = public` to prevent search-path injection. Each function is narrow in scope and returns only boolean or scalar values.

## ADR-004: Atomic Invoice Number Generation via Row-Level Locking
**Date:** 2026-08-08
**Status:** Adopted

Invoice numbers are generated by `generate_invoice_number(p_business_id)` using:
```sql
UPDATE businesses
SET invoice_counter = invoice_counter + 1
WHERE id = p_business_id
RETURNING invoice_counter, invoice_prefix;
```

**Format:** `{prefix}-{LPAD(counter, 4, '0')}` — e.g. `INV-0001`, `INV-0042`, `INV-10001`.

**Rationale:** PostgreSQL sequences are global and cannot be scoped per business. The `UPDATE … RETURNING` pattern acquires a row-level lock on the `businesses` row for the duration of the transaction. Concurrent transactions block and each receive a unique counter value. This guarantees uniqueness without a global sequence and without application-level coordination.

**Constraint:** The unique constraint `(business_id, invoice_number)` serves as a database-level backstop in case the trigger is ever bypassed.

## ADR-005: Database-Level Status Transition Enforcement
**Date:** 2026-08-08
**Status:** Adopted

Invoice status transitions are validated in the `before_invoice_change()` BEFORE trigger, not in Edge Functions.

**Valid transitions:**
| From | To |
|---|---|
| draft | sent, cancelled |
| sent | paid, overdue, void, cancelled |
| overdue | paid, void, cancelled |
| paid | void |
| void | *(terminal)* |
| cancelled | *(terminal)* |

**Rationale:** Edge Functions can be bypassed if the client calls the Supabase API directly. The database trigger is the final authority. Edge Functions may still validate for better error messaging, but the database always enforces correctness.

## ADR-006: Invoice Deletion Policy
**Date:** 2026-08-08
**Status:** Adopted

- `draft` invoices: physically deletable by any member (RLS DELETE policy allows it).
- All other statuses: no DELETE policy exists. The `invoices` table has no RLS DELETE policy for non-draft rows, making deletion impossible regardless of role.

**Rationale:** Finalized invoices are audit records. Physical deletion is irreversible and could create compliance issues. Voiding or cancelling is the correct path for closing an invoice.

## ADR-007: Snapshot Pattern for invoice_items
**Date:** 2026-08-08
**Status:** Adopted

`invoice_items` stores its own copies of `name`, `description`, `unit_price`, `unit`, and `tax_rate` from the `products` table at the time the item is added to the invoice.

**Rationale:** If `products.unit_price` changes, all existing invoice calculations must remain correct. By copying the values into `invoice_items`, the invoice becomes a self-contained historical document independent of future product changes. `product_id` is kept as a nullable FK for reference only.

## ADR-008: Automatic Total Computation via Triggers
**Date:** 2026-08-08
**Status:** Adopted

`invoice_items.line_total` and `invoice_items.tax_amount` are computed by the `before_invoice_item_change` trigger:
```
line_total = ROUND(quantity × unit_price × (1 - discount_rate / 100), 2)
tax_amount = ROUND(line_total × tax_rate / 100, 2)
```

`invoices.subtotal`, `invoices.tax_amount`, `invoices.total_amount` are synced by `sync_invoice_totals` after every item change.

`invoices.amount_paid` is synced by `sync_invoice_amount_paid` after every payment change.

**Rationale:** Storing computed totals server-side prevents client-side rounding errors or manipulated values. The database is always the source of truth for all monetary amounts. The application should never write `line_total`, `tax_amount`, `subtotal`, `total_amount`, or `amount_paid` directly.

## ADR-009: Single Tax Rate per Line Item (MVP)
**Date:** 2026-08-08
**Status:** Adopted for MVP

Each `invoice_item` has one `tax_rate` (percentage) and one computed `tax_amount`. Different line items may have different rates.

**Not in scope for MVP:** compound taxes (CGST/SGST/IGST/cess), tax tables, or automatic tax jurisdiction lookups.

**Future migration path:** If compound taxes are needed, add an `invoice_item_taxes` child table with `(invoice_item_id, tax_name, tax_rate, tax_amount)` rows and deprecate `invoice_items.tax_rate`.

## ADR-010: Soft-Delete for customers and products
**Date:** 2026-08-08
**Status:** Adopted

Customers and products use `is_active = false` as a soft-delete flag. The FK RESTRICT on `invoices.customer_id` prevents hard-deletion of a customer with invoices.

**Rationale:** Preserves the integrity of historical invoice data while allowing the business to "remove" entries from active use.
